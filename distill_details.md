# Knowledge Distillation Implementation Details

## Overview

The distillation module (`distill.py`) implements **response-level offline knowledge distillation** from DeepSeek-V4-Pro, a large teacher model, to improve the training data quality for the Qwen2.5 student model. Rather than modifying the training loss or architecture, this approach generates higher-quality target responses offline and trains the student on them using the existing SFT pipeline — a simple yet effective strategy that requires no changes to the training loop.

## Motivation

The original training data in `data/raw/` contains `output` fields generated by a smaller model. These outputs may lack depth, accuracy, or pedagogical quality. By having a much stronger teacher model (DeepSeek-V4-Pro) regenerate responses to the same instruction/input/context triples, we produce training targets that are richer, more accurate, and better structured for educational use. The student model then learns to mimic these higher-quality responses through standard supervised fine-tuning.

## Architecture

```
data/raw/*.jsonl  ──>  distill.py  ──>  data/processed/distilled_data.jsonl
                         │
                         ├── build_teacher_prompt()     # prompt construction
                         ├── call_deepseek_api()        # async API with retries
                         ├── checkpoint system           # resumable processing
                         └── cost estimation             # budget tracking
                         │
                         v
                   sft_train.py  (uses distilled_output field)
```

The distillation runs as **Stage 0.5** in the pipeline — before data preprocessing — so that `distilled_data.jsonl` is available when `data_preprocess.py` loads and splits the data.

## DeepSeek API Integration

### API Details

- **Endpoint:** `https://api.deepseek.com/chat/completions` (OpenAI-compatible)
- **Authentication:** Bearer token via `DEEPSEEK_API_KEY` environment variable
- **Models:** `deepseek-v4-pro` (stronger, more expensive) or `deepseek-v4-flash` (cheaper)
- **Thinking mode:** When enabled, the API returns a `reasoning_content` field containing the model's chain-of-thought reasoning, in addition to the final `content`

### Thinking Mode vs Standard Mode

When `thinking_mode: true` (the default):

- The request includes `"thinking": {"type": "enabled"}` and `"reasoning_effort": "high"`
- `temperature` and `top_p` are **omitted** — DeepSeek ignores them in thinking mode
- The response includes both `content` (the final answer) and `reasoning_content` (the reasoning chain)
- Both are saved to the output; `distilled_reasoning` is preserved for potential future use (e.g., reasoning distillation)

When `thinking_mode: false`:

- Standard sampling parameters (`temperature: 0.7`, `top_p: 0.9`) are sent instead
- Only `content` is returned; `distilled_reasoning` is empty

## Prompt Engineering

### System Prompt

A Chinese-language system prompt establishes the teacher's role as an educational QA expert:

```
你是一位专业的中国教育问答助手。请根据提供的参考资料，生成高质量、准确、详细的教育问答回答。
要求：
1. 回答必须基于参考资料中的事实信息
2. 使用清晰的中文，适当使用markdown格式
3. 包含关键知识点的解释和扩展
4. 如果参考资料是外文，请准确翻译并整合信息
5. 回答应具有教育价值，适合学生学习使用
```

The prompt emphasizes: factual grounding in the reference material, clear Chinese with markdown formatting, knowledge expansion, translation of foreign sources, and educational value.

### User Message Construction

The `build_teacher_prompt()` function assembles the user message from three optional parts:

1. **参考资料 (Reference material):** The `raw_content` field — labeled knowledge context from the original dataset
2. **问题 (Question):** The `instruction` field — the educational question
3. **附加输入 (Additional input):** The `input` field, if non-empty

These are joined with double newlines and end with a directive: "请生成一个高质量的教育回答" (Please generate a high-quality educational answer).

The resulting message structure:
```
参考资料：
{raw_content}

问题：{instruction}

附加输入：{input}          ← only if non-empty

请生成一个高质量的教育回答：
```

## Async Architecture

### Concurrency Model

The script uses Python's `asyncio` with `aiohttp` for non-blocking HTTP requests:

- **`asyncio.Semaphore(max_concurrent)`** limits the number of in-flight API requests (default: 5)
- **Batch processing:** Pending entries are processed in batches of `min(max_concurrent * 10, 100)`. Within each batch, all requests are dispatched concurrently via `asyncio.gather()`
- **Checkpoint after each batch:** Progress is saved atomically after each batch completes, ensuring no work is lost on interruption

### Request Flow

```
for each batch:
    tasks = [call_deepseek_api(entry) for entry in batch]
    results = await asyncio.gather(*tasks)   # concurrent execution
    update checkpoint
    save checkpoint (atomic write)
```

The semaphore is acquired inside `call_deepseek_api()` (within the `async with semaphore:` block), so the concurrency limit applies across all batches.

### Atomic Checkpoint Writes

Checkpoint files are written atomically to prevent corruption on crash:

```python
tmp_path = checkpoint_path + ".tmp"
with open(tmp_path, "w", encoding="utf-8") as f:
    json.dump(checkpoint, f, ensure_ascii=False, indent=2)
os.replace(tmp_path, checkpoint_path)  # atomic on both Windows and Unix
```

## Retry and Error Handling

### Exponential Backoff with Jitter

The `call_deepseek_api()` function implements robust retry logic:

- **Retryable conditions:** HTTP 429 (rate limit), HTTP 5xx (server error), `asyncio.TimeoutError`, and any other exception
- **Backoff formula:** `min(base_backoff * (2 ** attempt) + random.uniform(0, 1), max_backoff)`
  - Default: base=1.0s, max=60.0s → waits of ~1s, ~2s, ~4s, ~8s, ~16s (plus jitter)
- **Retry-After header:** For 429 responses, the `Retry-After` header is respected if present
- **Final attempt optimization:** On the last retry attempt, the function returns immediately with the error rather than sleeping uselessly

### Per-Entry Error Isolation

Individual API failures do not abort the entire distillation run:

- Failed entries get an empty `distilled_output` with the error message recorded
- During training, entries with empty `distilled_output` fall back to the original `output` field
- The checkpoint tracks both successful and failed entries with full error details

### Error Return Structure

Every code path in `call_deepseek_api()` returns a consistent structure:

```python
{
    "content": str,              # empty on error
    "reasoning_content": str,    # empty on error
    "usage": dict | None,        # None on error
    "error": str | None,         # None on success
    "latency": float,            # seconds
}
```

```json
            "distilled_reasoning": "",

```

### Resumability

On restart, the script:

1. Loads the existing checkpoint
2. Filters out entries that already have a successful result (non-empty `distilled_output` with no error)
3. Re-processes entries that previously failed (had an error and empty `distilled_output`)
4. Skips entries that succeeded even if they also have an error recorded (edge case: partial success)

This means:
- **Crash recovery:** Simply re-run the same command; it picks up where it left off
- **Failed retry:** Entries that failed due to transient errors get another chance
- **No duplicate work:** Successfully processed entries are never re-sent to the API

## Output Format

Each line in `distilled_data.jsonl`:

```json
{
    "instruction": "原始指令",
    "input": "原始输入",
    "output": "原始输出（保留作为后备）",
    "raw_content": "参考资料原文",
    "distilled_output": "DeepSeek生成的高质量回答",
    "distilled_reasoning": "DeepSeek的推理过程（thinking mode）"
}
```

Key design decisions:
- **Original `output` is preserved** as a fallback — if `distilled_output` is empty (due to API failure), the training pipeline uses the original output
- **`distilled_reasoning`** is stored for potential future use (e.g., reasoning-aware distillation, analysis) but is not currently consumed by training
- **All original fields** (`instruction`, `input`, `raw_content`) are carried through unchanged

## Integration with Training Pipeline

### Pipeline Stage Order

```
Stage 0.5: distill.py          # generate distilled_data.jsonl
Stage 1:   data_preprocess.py   # load distilled_data.jsonl, split into train/val/test
Stage 2:   rag/rag_db.py        # build RAG knowledge base
Stage 3:   test_eval.py         # pre-training benchmark
Stage 4:   sft_train.py         # train on distilled outputs
Stage 5:   model_utils.py       # merge LoRA
Stage 6:   test_eval.py         # post-training evaluation
```

### Config Flags

In `configs/config.yaml`:

```yaml
distill:
  enabled: false               # master switch for distillation stage
  # ... (all API/config options listed above)

dataset:
  use_distilled_data: false    # true = use distilled_output in training
```

Both must be `true` for a full distillation-and-train pipeline run. Setting `use_distilled_data: true` without `distill.enabled: true` assumes the distilled data file already exists from a prior run.

### Data Flow

1. `distill.py` reads `data/raw/*.jsonl`, writes `data/processed/distilled_data.jsonl`
2. `data_preprocess.py` checks `use_distilled_data` flag:
   - If `true` and `distilled_data.jsonl` exists → loads from it
   - If `true` but file missing → warns and falls back to raw data processing
   - If `false` → normal processing from raw data
3. `sft_train.py`'s `formatting_prompts_func` selects the output field:
   - If `use_distilled_data` and `distilled_output` is non-empty → uses `distilled_output`
   - Otherwise → uses original `output`
4. Same logic in `test_eval.py`'s `calculate_perplexity` for evaluation

### Graceful Degradation

The system is designed to degrade gracefully:

- **API failures:** Individual entries fall back to original `output`
- **Missing distilled file:** Pipeline falls back to raw data processing
- **Partial distillation:** Entries with `distilled_output` use it; others use original `output`
- **Cost too high:** User can abort at the confirmation prompt

## Usage

```bash
# Set API key
set DEEPSEEK_API_KEY=sk-...

# Run with confirmation prompt
python distill.py --config configs/config.yaml

# Run without confirmation (for automation)
python distill.py --config configs/config.yaml --yes

# Full pipeline with distillation
# (set distill.enabled: true and dataset.use_distilled_data: true in config)
python main.py --config configs/config.yaml

# Train on existing distilled data (distillation already done)
# (set dataset.use_distilled_data: true, distill.enabled: false)
python sft_train.py --config configs/config.yaml --timestamp "20260514120000"
```

## Key Design Decisions

1. **Offline distillation over online:** Pre-generating all teacher responses avoids the complexity of running two models simultaneously during training. The distilled data file is a drop-in replacement for the training data.

2. **Preserving original outputs:** The `output` field is kept as a fallback, so training never breaks even if distillation partially fails. This also enables A/B comparison between original and distilled data.

3. **Thinking mode by default:** DeepSeek's thinking mode produces more thorough, structured responses at the cost of slightly higher latency. The reasoning chain is preserved in `distilled_reasoning` for potential future use.

4. **Batch + checkpoint architecture:** Processing millions of API calls requires resumability. The batch-checkpoint pattern ensures progress is never lost, and the batch size (10x concurrency) balances checkpoint frequency against I/O overhead.

5. **Semaphore-based concurrency:** Rather than a fixed thread pool, asyncio.Semaphore provides fine-grained concurrency control that integrates naturally with aiohttp's async session.
